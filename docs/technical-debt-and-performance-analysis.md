## Executive Summary

A comprehensive architectural and performance analysis of the `Cpu6502` 6502 CPU emulator solution was conducted. The codebase exhibits strong modular design, clear separation of concerns, high unit test coverage (948+ passing unit tests), and accurate cycle timing metadata. 

However, several **critical performance bottlenecks, memory allocation hot spots, and technical debt items** were identified that impair emulation throughput and introduce unnecessary Garbage Collection (GC) pressure. 

Optimizing these areas can yield an estimated **35%–60% performance improvement** in CPU execution speed and **eliminate ~12 MB/sec of heap garbage generation** during frame rendering.

## 1. Hot-Path Performance Bottlenecks

### 1.1 Cycle Metadata Table Lookup Overhead (High Impact)
* **File:** `src/Cpu6502.Core/Cpu.CycleMetadata.cs`
* **Issue:** `GetCycleInfo(AddressingMode mode, AccessType access)` retrieves instruction timing by querying a `Dictionary<(AddressingMode, AccessType), CycleInfo>` tuple key.
* **Impact:** Every single CPU instruction execution requires hashing a 2-tuple, performing a dictionary bucket lookup, and evaluating equality. In C#, dictionary lookups incur substantial overhead compared to array indexing.
* **Recommendation:**
  Replace `Dictionary<(AddressingMode, AccessType), CycleInfo>` with a fixed 2D array or flat lookup table:
  ```csharp
  private static readonly CycleInfo[,] CycleLookupTable = new CycleInfo[11, 3];
  
  [MethodImpl(MethodImplOptions.AggressiveInlining)]
  public static CycleInfo GetCycleInfo(AddressingMode mode, AccessType access)
      => CycleLookupTable[(int)mode, (int)access];
  ```

---

### 1.2 Dual Bus Read on Instruction Fetch (High Impact)
* **File:** `src/Cpu6502.Core/Cpu.cs` (lines 85–93)
* **Issue:** Inside `Cpu.Step()`, the instruction fetch sequence performs:
  ```csharp
  byte opcode = Peek();  // 1st bus read (read without PC increment)
  _trace.OnInstructionFetched(pcBefore, opcode);
  if (_trace.ShouldBreak(pcBefore, opcode, A)) throw new BreakException(...);
  Fetch();               // 2nd bus read (read WITH PC increment)
  ```
* **Impact:** Every single CPU instruction performs **two bus read operations** (`_bus.Read(PC)`) just to support tracing and conditional breakpoints, effectively doubling the memory fetch overhead.
* **Recommendation:**
  Fetch the opcode once, advance `PC`, and pass the cached opcode byte to trace hooks:
  ```csharp
  byte opcode = ReadByte(PC++);
  _trace.OnInstructionFetched(pcBefore, opcode);
  if (_trace.ShouldBreak(pcBefore, opcode, A)) throw new BreakException(...);
  ```

---

### 1.3 Opcode Dispatch Table (`Action[] _ops` Delegates) (Medium-High Impact)
* **File:** `src/Cpu6502.Core/Cpu.cs` (line 31)
* **Issue:** Opcodes are dispatched through an array of `Action` delegates: `_ops[opcode]()`.
* **Impact:** In .NET, delegate invocation cannot be inlined by the JIT compiler and incurs virtual call overhead. Jump tables generated by direct `switch (opcode)` statements or C# 9+ function pointers (`delegate*<void>`) execute significantly faster.
* **Recommendation:**
  * **Option 1 (Method References / Hybrid):** Retain partial class layout but use cached method delegates without lambda closures.
  * **Option 2 (Direct Switch Dispatch):** Implement a direct `switch (opcode)` dispatch loop in `Step()`. This allows the .NET JIT compiler to emit a native hardware jump table (e.g. `jmp qword ptr [rax + rbx*8]`) and inline small opcode bodies (e.g., `NOP`, `TAX`, `INX`, `CLC`).

---

### 1.4 Address Decoder Struct Deconstruction Overhead (Medium Impact)
* **File:** `src/Cpu6502.Core/AddressDecoder.cs` (lines 33, 48)
* **Issue:** Memory access methods deconstruct the routing record struct on every `Read` and `Write`:
  ```csharp
  var (device, from) = _routes[address];
  ```
* **Impact:** `Route` is a `readonly record struct Route(IBus? Device, ushort From)`. Deconstructing copy-assigns interface pointers and `ushort` offsets millions of times per second.
* **Recommendation:**
  Use `ref readonly` or direct property access:
  ```csharp
  ref readonly var route = ref _routes[address];
  if (route.Device is not null)
  {
      ushort offset = (ushort)(address - route.From);
      return route.Device.Read(offset);
  }
  ```

---

### 1.5 Interface Virtual Call Overhead on RAM/ROM Access (Medium Impact)
* **File:** `src/Cpu6502.Core/AddressDecoder.cs` & `Ram.cs` / `Rom.cs`
* **Issue:** `AddressDecoder` routes all memory traffic through the `IBus` interface (`device.Read(offset)`).
* **Impact:** The vast majority (~90%+) of CPU memory accesses are to RAM or ROM. Interface dispatch prevents JIT inlining for basic array indexing.
* **Recommendation:**
  Introduce direct fast-path RAM/ROM routing inside `AddressDecoder` or expose direct `byte[]` memory span pointers for flat memory regions, bypassing interface calls for standard RAM/ROM reads.

## 2. Memory Allocations & GC Pressure

### 2.1 Per-Frame Heap Allocation in Video Rendering (High Impact)
* **File:** `src/Machines.Atom/Mc6847.cs` (line 183)
* **Issue:** The MC6847 video chip renderer allocates a new pixel array on every frame render call:
  ```csharp
  public void RenderFrame(IVideoSink sink)
  {
      uint[] pixels = new uint[256 * 192]; // Allocates ~196 KB every frame!
      ...
  }
  ```
* **Impact:** Running at 60 FPS creates **~11.7 MB of heap garbage per second**, causing frequent Generation 0/1 Garbage Collector pauses during video playback.
* **Recommendation:**
  Reuse a single instance-level array buffer:
  ```csharp
  private readonly uint[] _pixelBuffer = new uint[256 * 192];
  ```

---

### 2.2 Delegates and Closures in Read-Modify-Write (RMW) Opcodes (Medium Impact)
* **File:** `src/Cpu6502.Core/Cpu.Arithmetic.cs` (lines 74–88) & `Cpu.Shifts.cs` (line 55)
* **Issue:** Memory modification opcodes (`INC`, `DEC`, `ASL`, `LSR`, `ROL`, `ROR`) pass lambda expressions to helper methods:
  ```csharp
  private void INC_Zp() { var a = AddrZeroPage(); RMW(a, v => ++v); ... }
  private void RMW(ushort address, Func<byte, byte> op) { ... }
  ```
* **Impact:** Calls `Func<byte, byte>` delegates on every RMW instruction execution.
* **Recommendation:**
  Inline RMW operations directly or use explicit non-delegate inline helper methods.

---

### 2.3 Per-Instruction Event Invocation (`OnCyclesConsumed`) (Medium Impact)
* **File:** `src/Cpu6502.Core/Cpu.cs` (line 104)
* **Issue:** `Cpu.Step()` invokes `OnCyclesConsumed?.Invoke(totalConsumed)` on every instruction.
* **Impact:** Multicast delegate invocation overhead per instruction.
* **Recommendation:**
  Batch cycle accounting to frame boundaries or integrate clock update logic without delegate invocation.

## 3. Technical Debt & Code Quality

### 3.1 Status Register Flags Representation
* **File:** `src/Cpu6502.Core/Cpu.cs` (lines 17–22)
* **Issue:** Status flags are stored as six individual `bool` fields (`C`, `Z`, `I`, `D`, `V`, `N`).
* **Impact:** Reading or writing processor status (`GetStatus()`, `SetStatus()`) requires multiple bitwise shifts and boolean evaluation branches. `SetZN()` is called by over 70% of instructions.
* **Recommendation:**
  Consolidate flags into a single byte field `byte P` or `StatusFlags` enum bitmask. Provide property getters/setters while performing bitwise operations directly on `P`.

---

### 3.2 Incomplete Acorn Electron Emulation Target
* **File:** `src/Machines.Electron/ElectronUla.cs`
* **Issue:** The Acorn Electron ULA is implemented in `Machines.Electron`, but there is currently no `Host.Electron` runnable CLI project or integrated host runner.
* **Recommendation:**
  Complete the Electron machine composite and host entry point, aligning with `Host.Atom` and `Host.Vic20`.

---

### 3.3 Vectorization & SIMD Opportunities in Display Pipeline
* **File:** `src/Adapters.Raylib/RaylibHost.cs` (lines 157–165 & 235–254)
* **Issue:** Pixel format conversion (ARGB32 to RGBA32) and CRT scanline darkening are performed using standard single-pixel `for` loops.
* **Recommendation:**
  Utilize `System.Runtime.Intrinsics` / `Vector128<uint>` or SIMD operations to process 4 to 8 pixels per cycle during texture update and scanline processing.
